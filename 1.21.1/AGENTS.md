# Universal Config プロジェクト実行ガイド

## 共有作業環境

- このリポジトリは複数人で共同開発する。個人環境だけで成立する設定、ユーザー名を含む絶対パス、IDE固有の必須設定を追加しない。
- Gradleはシステムへインストールされたコマンドではなく、リポジトリのWrapperを使う。Windowsでは `.\gradlew.bat`、Unix系では `./gradlew` を実行する。
- コンパイル対象はJava 21である。JDKを変更する場合は、`build.gradle`、CI、READMEの要件を同時に確認する。
- 依存関係とGradleプラグインは再現可能な固定バージョンを使う。動作確認なしに `SNAPSHOT`、動的バージョン、ローカルキャッシュ依存へ変更しない。
- 認証情報、Webhook URL、個人用Codex設定、IDEキャッシュ、`run/`、`build/`、`.gradle/` をコミットしない。
- ユーザーの未コミット変更を作業開始時に確認し、依頼と無関係な差分を変更、整形、ステージ、破棄しない。
- コミットメッセージ、PRのタイトルと本文、レビューでの説明は原則として日本語で記載する。外部仕様の固有名詞、コード、コマンド、識別子は無理に翻訳しない。

## 検証とテストプレイ

- Javaまたはビルド設定を変更したら `.\gradlew.bat check` と `.\gradlew.bat build` を実行する。片方を省略した場合は理由を報告する。
- PRと `main` へのpushではGitHub Actionsのビルドを通す。ローカル成功だけで共有可能と判断しない。
- UIや起動時処理を変更したら、ビルド後に `runClient` でテストプレイし、`run/logs/latest.log` に新しい例外がないことを確認する。
- 自動実行でテストプレイを起動するときは、起動用PowerShellを常駐させたり `-NoExit` を使ったりしない。Windowsでプロセスを分離する場合は、非表示の `cmd.exe /c gradlew.bat runClient` を使い、起動元を終了できる形にする。
- 既にMinecraftテストクライアントが起動している場合は、二重起動せず既存プロセスとログを確認する。

## ハードコードを避ける

### 表示文言

- 画面名、ボタン、説明、警告、エラー、確認メッセージなど、ユーザーに見える文言を Java コードへ直接書かない。
- 表示文言には `Text.translatable("...")` を使用する。`Text.literal(...)` はユーザー入力、ファイル名、バージョン番号など、翻訳してはいけない動的な値に限定する。
- 新しい翻訳キーは、必ずすべての言語へ同時に追加する。
- 翻訳キーは `screen.universal_config.*`、`button.universal_config.*`、`message.universal_config.*` など、用途が分かる一貫した名前にする。
- 動的な値は文字列連結せず、翻訳キーのプレースホルダーへ渡す。

```java
// NG: 表示言語を変更できず、文言の管理場所も分散する。
Text.literal("Delete profile " + profileName + "?");

// OK: profileName は翻訳対象ではない動的な値として渡す。
Text.translatable("message.universal_config.confirm_delete", profileName);
```

### 定数と識別子

- Mod ID、翻訳キー、ファイル名、拡張子、設定キー、画面寸法などを複数箇所へ重複して書かない。意味のある定数または共有ヘルパーへまとめる。
- ただし、一度しか使わず意味も明白な値まで定数化しない。
- Identifier、設定パス、リソースパスは文字列連結で組み立てず、既存の定数やパスAPIを使う。
- OS固有の絶対パス、開発者環境のパス、ユーザー名をコードへ埋め込まない。

## Fabric・Minecraft実装の注意点

- このModはクライアントModである。クライアント専用クラスを共通のコア処理から参照しない。
- tickイベントでは重いファイルI/O、ZIP処理、ディレクトリ走査を繰り返さない。
- 画面や `MinecraftClient` の状態変更はクライアントスレッド上で行う。
- ゲームの内部状態へ変更を加えた場合は、Minecraft側の保存・再読み込み順序を確認する。特に `options.txt` は終了時にMinecraftが再保存するため、読み込み後の `options.load()`、キー更新、`options.write()` の既存順序を不用意に変更しない。
- ボタンの連打や画面再初期化で処理が二重実行されないようにする。
- GUI座標は固定解像度を前提にせず、`width`、`height`、既存のレイアウトヘルパーから計算する。
- ボタン文言が長い言語でも操作不能にならないよう、幅、折り返し、省略の必要性を確認する。
- キーボード操作、Escで戻る動作、ナレーションを壊さない。アイコンだけの操作には支援技術向けの名前を設定する。

## リソースとデータ

- `universal_config` 名前空間を使用し、Mod IDを別表記で増やさない。
- リソースを追加したら、パス、大文字小文字、`fabric.mod.json` からの参照を確認する。Windowsで動いても、大文字小文字を区別する環境で失敗する名前にしない。
- JSONは構文だけでなく、Minecraft/Fabricが期待するキーと配置も確認する。
- `fabric.mod.json`、`gradle.properties`、READMEの対応バージョンを変更するときは、互いに矛盾させない。
- 画像や音声などのバイナリリソースを追加する場合は、不要に大きなファイルを含めない。

## ファイル操作と安全性

- `.ucp` と `.ucbackup` は外部入力として扱い、内容を信頼しない。
- ZIPエントリは必ず `ZipSecurity` で検証し、絶対パス、`..`、展開先外への書き込みを拒否する。
- 削除、復元、上書きの前に、正規化したパスが許可されたディレクトリ配下にあることを確認する。
- Universal Config自身の設定ファイルと適用予約ファイルを、プロファイルやバックアップへ含めない。
- 失敗を無視せず、`UniversalConfigException` にユーザーが対処できる文脈を持たせる。内部例外の詳細をそのまま画面へ表示しない。
- ファイル操作は `FileOperationLogger` へ記録する。ファイル内容、認証情報、個人情報はログへ出さない。

## UI文言と操作

- UIには操作や判断に必要な情報だけを表示し、見出し、説明、ボタンで同じ内容を繰り返さない。
- ボタンは「変更内容を保存する」ではなく「保存」のように短くする。
- 削除、復元、適用など、データを失う可能性がある操作は実行前に確認する。
- 互換性警告、適用予定の差分、バックアップの有無など、ユーザーの判断に必要な情報は省略しない。
- 成功通知は短くする。エラーは内部実装ではなく、ユーザーが次に取れる行動を伝える。

## コメント

- 処理内容を読み上げるコメントではなく、Minecraft/Fabricの制約、処理順が重要な理由、安全対策、互換性上の判断を記録する。
- 一見不要に見える再読み込み、パス検証、バックアップ、イベント発火抑制には、削除してはいけない理由をコメントする。
- 仕様変更時は関連コメントも確認し、古くなった説明を残さない。

## 互換性とModメタデータ

- 新しいMinecraftバージョン、Modローダー、前提Modへ対応するときは、実際に動作する最低バージョンを確認し、不要な上限・下限を設けない。互換性を損なわない場合は `*`（Any）を優先する。
- ビルドに必要な依存バージョンを固定する場合でも、配布JarのModメタデータでは、実行に必要な最低バージョンだけを指定する。ビルド用の固定バージョンと実行時の依存条件を混同しない。
- Fabric、Forge、NeoForgeなど別のModローダー向けのModを作る場合も、説明、作者・メンバー、リンク、ライセンス、アイコンなどのMod情報を各ローダーの形式で揃える。非公開URLや利用者がアクセスできないリンクは公開メタデータへ設定しない。
- 複数のMinecraftバージョンで動作させられる場合は、可能な範囲で複数バージョンに対応する。対応できない場合は、対象バージョン、理由、最低要件をModメタデータとビルド設定で一致させる。
- ローダーやMinecraftバージョンを追加・変更した場合は、各バージョンのModメタデータ、依存関係、説明、リンク、アイコン、配布Jarを確認し、表記の不一致を残さない。
